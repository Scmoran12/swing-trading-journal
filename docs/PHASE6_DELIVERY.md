# Phase6 — opt-in desktop notification tests

17 October2026. User authorized the next phase and requested that every final handoff state the next phase and how many remain. v0.6 adds a **synthetic desktop-test pipeline**, not automatic trading alerts. The actual Windows adapter/display/human receipt remains unverified here. iPhone HTTPS/PWA/push remains conditional and unimplemented; no public network or paid service is introduced.

## Implemented

- An owner-only `/desktop-tests` page, linked from the existing inbox without replacing it. Desktop tests default **off**. The owner explicitly enables them and queues a fixed test valid for ten minutes. Multiple clicks/retries deduplicate the active logical test. Limits: one queued/leased/accepted test at a time,20 tests per rolling24h,200 retained; no automatic archival UI.
- New forward migration0006 adds preferences, test outbox, attempts, events and idempotent commands with forced owner RLS and bounded server commands. Runtime cannot directly write/delete these tables. Delivered migrations0001–0005 and dependency versions remain unchanged; no financial/review/monitoring tables are modified.
- A manually invoked, one-shot Windows sender `npm run desktop:test`. It loads the existing private OS-account configuration, discards the migration connection, uses restricted auth/runtime roles and processes at most one queued test. Missing test settings, mismatched DB targets or a personal DB under --test fail closed; inherited personal credentials are never a test fallback. It installs no task/service and does not poll, open the browser, invoke Codex/plugins or request market data.
- The Windows adapter uses built-in PowerShell/WinRT with an explicitly selected **existing registered AppID**. It changes no registry entries, execution policy or notification permissions and installs no module. The chosen host's app name, for example PowerShell, labels the OS notice; the fixed message is SwingPilot TEST ONLY plus a random code and a request to open the local page. No balances, holdings, emotions, notes, attachments, account IDs or executable/deep-link actions are sent.
- A60-second lease with an unpredictable token fences completion and preference revocation. One attempt is made per CLI invocation. Known pre-send failures allow an explicit retry, maximum3 attempts. Timeout, crash or lease loss is UNKNOWN, with no automatic retry. Windows tags reduce duplicate display but cannot establish exactly-once physical delivery. Disable/cancel cannot recall an already accepted notice or atomically stop a send already in progress.
- Sender acceptance and human receipt are separate. A six-digit challenge is sent only in the OS notice; stdout/API do not reveal it, and DB stores a test-bound SHA-256. The owner can enter it and report whether the website was open/closed/unknown. Five wrong attempts lock that challenge. A matching code records **human-reported receipt**, not independently measured OS telemetry or proof against a dishonest/local privileged owner. A structurally valid simulated receipt is never physical-device acceptance evidence.
- Expired tests cannot be sent/retried/acknowledged; explicit reconciliation preserves attempt ambiguity. The browser cannot call CLAIM/FINISH or supply arbitrary titles, trading recommendations, payloads, tokens or trust flags. Existing inbox history and financial records remain unchanged by all test actions.

## Verification actually performed

Cloud production build/TypeScript passed. **49 unit/security/risk/market/AI/schedule/notification cases**, PostgreSQL **9 desktop +8 foundation +19 lifecycle +9 monitoring +12 review** cases, and **13 production HTTP** cases passed. Node counts include parents. All data/configuration was synthetic/disposable. Tests cover populated v0.5 upgrade/replay, default-off consent, durable queue/dedup, concurrent claims, token fencing, no code/token leakage, sender-accepted versus code receipt, persistent wrong-code lockout, expired/unknown outcomes, manual retry caps, revocation and unchanged finances. HTTP receipt fixtures explicitly simulate acceptance; no actual Windows sender was invoked.

Adapter tests inject a fake process runner or assert Linux rejection. They verify fixed payload/privacy, malformed/ambiguous outcome handling, input bounds and no code in results. **The PowerShell/WinRT script has not been executed or syntax/runtime-validated on Windows in this cloud chat.** Registered AppID availability, permissions/Focus Assist, actual display with all tabs closed, locked-session behavior and human receipt remain Windows acceptance gates. There is no verified phone delivery, native scheduler, production outbox or automatic market alert.

Temporary database/server resources were stopped and removed. No real notification, provider call, native model run, purchase, public exposure, recurring task or backup operation occurred here. No fresh dependency audit is claimed; dependency versions are unchanged.
